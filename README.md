# Предпроектная спецификация требований и архитектуры
## Разработка интеграции аккаунтов Milestone Team с Milestone Launcher

**Software Requirements & Architecture Specification (SRS/AS)**  
**Тема практики:** «Осуществление интеграции программных модулей».  
**Объект проектирования:** модуль авторизации Milestone Launcher через систему аккаунтов Milestone Team.  
**Версия документа:** 1.0.  
**Этап:** анализ требований и проектирование, до начала реализации.

## 1. Назначение документа

Документ определяет требования к разработке интеграции аккаунтов сайта Milestone Team с настольным лаунчером, состав программных модулей, контракты их взаимодействия, меры защиты и порядок приёмки. Он предназначен для разработчика лаунчера, разработчика серверной части, тестировщика и администратора.

Для учебного проекта принимается исходное состояние до появления интеграции: сайт и лаунчер существуют как отдельные компоненты, но вход в лаунчер с аккаунтом сайта ещё не реализован. Технические сведения о проектах используются как основа выбора технологий. Все описанные далее механизмы интеграции являются проектными решениями и требованиями к будущей реализации. Документ не является отчётом об уже выполненном программировании или испытаниях.

## 2. Анализ проблемы и исходного состояния

### 2.1. Проблема

Отсутствие связи между системой аккаунтов сайта и лаунчером не позволяет использовать единые учётные данные и централизованно определять доступ пользователя к игровым проектам. Статус аккаунта на сайте не учитывается при работе лаунчера. Администрации требуется единый механизм одобрения и блокировки пользователей, а игрокам — понятный способ входа без создания дополнительной учётной записи.

Разработка интеграции должна устранить разрыв между регистрацией пользователя на сайте и предоставлением ему доступа через лаунчер.

### 2.2. Исходные компоненты и ограничения

| Компонент | Технологическая основа | Значение для проекта |
|---|---|---|
| Milestone Launcher 2025.3.3 | C#, .NET 8, Avalonia 11.3.3 | База для разработки формы входа, клиента API и управления сессией |
| Gml.Client | Библиотека взаимодействия с серверной частью | Расширяется адаптером авторизации и проверки сессии |
| Gml.Backend | Серверная часть экосистемы Gml | Используется как посредник между лаунчером и системой аккаунтов; при необходимости дорабатывается |
| Сайт Milestone Team | PHP, веб-интерфейс аккаунта | На его стороне проектируется сервис проверки учётных данных и допуска |
| Серверное хранилище | SQLite через PDO | Используется для аккаунтов, статусов и служебных данных интеграции |
| Клиентское хранилище | SQLite, sqlite-net-pcl 1.9.172 | Используется для несекретных настроек; токен хранится отдельно средствами ОС |
| Веб-сервер | Apache либо эквивалентная конфигурация | Обеспечивает HTTPS и закрывает доступ к внутренним каталогам |

Базовая клиентская платформа первой версии — Windows x64. Перенос защищённого хранения на Linux и macOS относится к последующим версиям. Серверная среда должна поддерживать PHP с PDO, pdo_sqlite и OpenSSL. Конкретные сборки runtime и backend фиксируются в манифесте стенда до реализации и сохраняются на протяжении приёмочных испытаний.

В проекте лаунчера указана лицензия Apache-2.0. Перед распространением требуется проверить лицензионные условия Gml.Backend, Gml.Client и всех включаемых зависимостей, сохранить обязательные уведомления. Наличие обозначения лицензии в одном проекте не распространяет её автоматически на остальные компоненты.

Ограничения: работа защищённых функций требует сети; SQLite допускает ограниченную конкуренцию записей; почтовое подтверждение зависит от доступности почтового сервиса. Действующий домен задаётся конфигурацией и не определяется по имени папки с исходниками.

## 3. Цель, участники и границы разработки

**Цель:** разработать интеграцию, позволяющую пользователю входить в Milestone Launcher с аккаунтом Milestone Team и получать доступ в соответствии с актуальным статусом этого аккаунта.

Заказчик учебного проекта — команда Milestone Team. Пользователь регистрируется и входит в лаунчер. Администратор одобряет и блокирует обычные аккаунты. Старший администратор (Councilor) дополнительно управляет персоналом. Администратор инфраструктуры отвечает за конфигурацию, HTTPS и восстановление.

В состав разработки входят:

- API проверки аккаунта на сайте и адаптер его вызова в backend;
- форма входа и отображение ошибок в лаунчере;
- выдача, защищённое хранение, проверка и отзыв сессий;
- учёт подтверждения почты, одобрения и блокировки;
- журналирование, конфигурация, инструкция развёртывания и тесты.

В первой версии не реализуются вход через Microsoft, перенос браузерной сессии, двухфакторная аутентификация и переработка игровых модулей. Вход выполняется по логину и паролю. Регистрация, подтверждение почты и управление аккаунтом доступны через сайт; лаунчер открывает соответствующие страницы в браузере.

## 4. Функциональные требования — ПК 4.3

| ID | Требование | Проверяемый результат |
|---|---|---|
| FR-01 | Лаунчер должен предоставлять поля логина и пароля, кнопку входа и ссылку регистрации | Пользователь может начать вход или открыть сайт регистрации |
| FR-02 | Пароль должен скрываться при вводе; пустые поля не отправляются | Локальная проверка показывает сообщение до обращения к серверу |
| FR-03 | Проверка учётных данных должна выполняться системой аккаунтов через backend | Клиент не обращается непосредственно к БД или внутреннему API сайта |
| FR-04 | Вход разрешается только при верном пароле, подтверждённой почте, одобрении и отсутствии блокировки | Нарушение любого условия не позволяет создать сессию |
| FR-05 | Аккаунт должен иметь постоянный UUID | Повторные входы и смена пароля не изменяют UUID |
| FR-06 | При успешном входе backend должен выдать сессию с ограниченным сроком | Лаунчер получает имя, UUID, модель скина, токен и время истечения |
| FR-07 | При перезапуске лаунчер должен проверять сохранённую сессию через backend | Действительная сессия восстанавливается, истёкшая или отозванная удаляется |
| FR-08 | Выход должен удалять локальный токен и отзывать серверную сессию | Повторное использование отозванного токена отклоняется |
| FR-09 | Блокировка, отзыв одобрения и смена пароля должны прекращать действие ранее созданных сессий | Защищённые операции прекращаются в срок не более 60 секунд |
| FR-10 | Ошибки должны иметь машинный код и понятное сообщение | Пользователь различает неверные данные, запрет доступа, лимит попыток и сбой сети |
| FR-11 | Во время входа повторная отправка должна блокироваться | Одно нажатие не порождает несколько параллельных запросов |
| FR-12 | Сервер должен проверять полномочия каждой административной операции | Обычный пользователь не может изменить чужой статус или роль |
| FR-13 | При отсутствии сети защищённые действия запрещаются | Сохранённая сессия сама по себе не даёт онлайн-доступ |
| FR-14 | Изменения статуса и роли должны фиксироваться в журнале аудита | Запись содержит исполнителя, объект, действие, время и результат без секретов |

### 4.1. Правила допуска

Допуск вычисляется по условию:

`правильный пароль AND email_verified AND approval_status = approved AND NOT is_blocked`.

Статус одобрения принимает значения `pending`, `approved`, `denied`. Новый аккаунт получает `pending`. Блокировка хранится отдельно и имеет приоритет над одобрением. Неподтверждённая почта запрещает вход независимо от роли. Для сотрудников одобрение может выполняться при назначении роли, но не должно обходить блокировку и подтверждение почты.

При неверных учётных данных возвращается общее сообщение без раскрытия существования логина. После успешной проверки пароля причины отказа проверяются в порядке: блокировка, подтверждение почты, одобрение.

### 4.2. Основной сценарий

1. Пользователь регистрирует аккаунт на сайте и подтверждает почту.
2. Администратор одобряет аккаунт.
3. Пользователь вводит логин и пароль в лаунчере.
4. Backend передаёт данные сервису аккаунтов по защищённому соединению.
5. Сервис проверяет пароль и условия допуска, возвращает сведения пользователя.
6. Backend создаёт сессию и возвращает токен лаунчеру.
7. Лаунчер сохраняет токен средствами ОС и открывает основной экран.

При отказе новый токен не создаётся. При сетевой ошибке форма остаётся доступной для ручной повторной попытки; пароль очищается после завершения попытки. Окончательный отказ по сессии очищает сохранённый токен. Временная недоступность сервера не считается доказанным отзывом, но до успешной проверки защищённые действия запрещены.

## 5. Архитектура решения

### 5.1. Развёртывание

![MD1](https://github.com/cuprummngl/practice/blob/main/md1.png)

Backend является единственной точкой входа для API лаунчера. Сайт является источником сведений об аккаунте и его статусе. Серверная сессия принадлежит backend. Ни лаунчер, ни браузер не получают доступ к БД или межсервисному секрету.

Сайт и backend допускается разместить на одном сервере, сохраняя разные конфигурации и права процессов. Наружу открывается HTTPS; файлы данных, конфигурации и резервные копии по HTTP недоступны.

## 6. Модель данных и управление сессиями

Система аккаунтов должна предоставлять следующие логические поля; существующие поля переиспользуются без создания дублирующих аккаунтов.

| Сущность | Поля и ограничения |
|---|---|
| Аккаунт | id; login и уникальный login_key; password_hash; уникальный UUID; email; email_verified_at; approval_status; is_blocked; role; is_slim; access_version |
| Попытка входа | login_key; идентификатор источника; время UTC; результат; срок хранения |
| Аудит | id; исполнитель; пользователь; действие; время UTC; результат |
| Сессия backend | hash токена; UUID; access_version; created_at; expires_at; revoked_at; last_status_check_at |

UUID генерируется один раз при создании аккаунта. Для сравнения логинов используется единая нормализация: удаление пробелов по краям и приведение регистра; пароль не обрезается и не меняет регистр. До создания уникального индекса выполняется проверка конфликтов логинов. При конфликте миграция останавливается с отчётом, записи не объединяются автоматически.

Токен — непрозрачная случайная последовательность с энтропией не менее 256 бит. Срок сессии — 24 часа без автоматического продления. В backend хранится SHA-256 токена; полный токен передаётся только клиенту. Если выбранная версия Gml использует иной формат, адаптер должен сохранить указанные свойства проверки и отзыва; нельзя полагаться только на подпись и срок JWT.

Изменение пароля, блокировка и изменение одобрения увеличивают `access_version`. Backend при каждом защищённом запросе проверяет срок и отзыв сессии и использует сведения о статусе аккаунта, закешированные не более чем на 60 секунд. После истечения кеша выполняется серверный запрос статуса; при недоступности сервиса доступ запрещается до успешной проверки. Несовпадение версии доступа отзывает сессию. Уже запущенный игровой процесс этим механизмом не завершается; отключение активного игрового соединения потребует отдельной интеграции игрового сервера.

При выходе без сети токен удаляется локально немедленно; серверный отзыв не объявляется успешным. Такая серверная сессия сохраняет действие до истечения срока или отдельного отзыва. При наличии сети отзыв должен завершиться до подтверждения полного выхода.

## 7. Контракты API

Ниже определяется целевой контракт разработки. При несовпадении с API выбранной версии Gml разработчик обязан реализовать преобразование в адаптере. Примеры содержат условные значения.

### 7.1. Общий формат

Все запросы используют HTTPS и UTF-8. JSON-запросы имеют `Content-Type: application/json`. Максимальный размер тела авторизации — 8 КиБ, ограничение применяется веб-сервером до чтения тела приложением. Время передаётся в UTC в ISO 8601. Ответы авторизации имеют `Cache-Control: no-store`.

Ошибка:

```json
{"error":{"code":"INVALID_CREDENTIALS","message":"Неверный логин или пароль"},"requestId":"идентификатор-запроса"}
```

`requestId` используется для диагностики; секреты и технические трассировки в ответ не включаются.

### 7.2. Лаунчер → backend

| Метод и маршрут | Вход | Успешный ответ |
|---|---|---|
| POST /api/v1/integrations/auth/signin | JSON: Login, Password | 200: user, accessToken, expiresAt |
| POST /api/v1/integrations/auth/checkToken | Authorization: Bearer TOKEN; тело {} | 200: user, expiresAt |
| POST /api/v1/integrations/auth/signout | Authorization: Bearer TOKEN; тело {} | 204 без тела; повторный отзыв также 204 |

`user` содержит `uuid` (UUID), `login` (строка), `isSlim` (boolean). Успешный `signin` возвращает `accessToken` только один раз для создаваемой сессии. Проверка токена не продлевает срок. HWID не используется как доказательство личности и не требуется для данной функции.

### 7.3. Backend → сайт

Внутренние методы требуют `X-Auth-Secret`. Секрет не включается в клиентскую сборку.

**POST /auth/api/authenticate.php**

```json
{"Login":"PracticeUser","Password":"<тестовый пароль>"}
```

Успех — HTTP 200:

```json
{"Login":"PracticeUser","UserUuid":"123e4567-e89b-42d3-a456-426614174000","IsSlim":false,"AccessVersion":1}
```

**POST /auth/api/status.php** — проектируемый метод проверки актуального допуска. Вход: `{"UserUuid":"123e4567-e89b-42d3-a456-426614174000"}`. Успех — HTTP 200 с полями `Allowed` (boolean), `AccessVersion` (целое), `ReasonCode` (строка либо null). Для отсутствующего UUID — 404; backend отзывает связанную сессию. Пароль при проверке статуса не передаётся.

### 7.4. Ошибки и преобразование

| HTTP | Код | Поведение клиента |
|---|---|---|
| 400 | INVALID_REQUEST | Сообщить об ошибке запроса; автоматический повтор запрещён |
| 401 | INVALID_CREDENTIALS | Предложить проверить данные |
| 401 | SESSION_INVALID | Очистить сохранённую сессию и открыть вход |
| 403 | ACCOUNT_BLOCKED / EMAIL_UNVERIFIED / APPROVAL_PENDING / APPROVAL_DENIED | Показать соответствующую причину и ссылку на аккаунт |
| 405 | METHOD_NOT_ALLOWED | Ошибка контракта; зафиксировать requestId |
| 415 | UNSUPPORTED_MEDIA_TYPE | Ошибка контракта; зафиксировать requestId |
| 429 | RATE_LIMITED | Показать время ожидания из Retry-After |
| 503 | AUTH_SERVICE_UNAVAILABLE | Сообщить о временной недоступности |

Внутренние 500, сетевой сбой сайта и отказ проверки межсервисного секрета backend преобразует в 503 для клиента. Неверный серверный секрет нельзя показывать как блокировку пользователя. Клиент не повторяет вход с паролем автоматически. Неизвестные поля ответа игнорируются, отсутствие обязательных полей считается ошибкой сервиса.

## 8. Нефункциональные требования — ПК 4.2

Показатели являются критериями будущей приёмки, а не результатами измерений.

| ID | Требование | Метод измерения |
|---|---|---|
| NFR-01 | p95 времени входа не более 2 с при RTT клиент–backend до 100 мс | 1000 успешных входов после прогрева; измерение полной цепочки |
| NFR-02 | 20 параллельных клиентов, суммарно 5 входов/с в течение 15 минут; неожиданные 5xx менее 1% | Нагрузочный тест с разными аккаунтами; сбор задержек, CPU, RAM и ошибок SQLite |
| NFR-03 | Полное ожидание входа не более 10 с | Имитация зависшего соединения; тайм-аут внутреннего вызова 5 с, общий клиентский 10 с |
| NFR-04 | Отзыв доступа к защищённым API не позднее 60 с | Изменение статуса активного аккаунта и запрос каждые 5 с |
| NFR-05 | RPO не более 24 ч, RTO не более 2 ч | Ежедневное резервирование и контрольное восстановление на отдельном стенде |
| NFR-06 | Сохранение UUID, статусов и целостности связей при обновлении | Сравнение контрольного набора до и после миграции |
| NFR-07 | Интерфейс остаётся отзывчивым при сетевом ожидании | Ручное испытание с задержкой; отсутствие блокировки UI-потока |

Базовый стенд: Windows x64 с 4 ГБ RAM для клиента; серверные компоненты — суммарно 2 vCPU, 4 ГБ RAM и SSD; тестовая база — 10 000 синтетических аккаунтов. Это проектная конфигурация для измерений, её достаточность должна быть подтверждена испытаниями. В протокол включаются точные версии и фактическое распределение ресурсов. Ожидаемые отказы 401/403/429 считаются отдельно от неожиданных серверных ошибок.

## 9. Спецификация программной защиты — ПК 4.4

| Область | Обязательное решение | Проверка |
|---|---|---|
| Пароли | Хеширование штатным password_hash; проверка password_verify; пароль не хранится на клиенте | Анализ БД, хранилища и журналов тестового входа |
| Локальный токен | Windows DPAPI в контексте пользователя; права файла только владельцу | Скопированный файл не раскрывает токен другому пользователю ОС |
| Каналы | HTTPS с проверкой цепочки и имени сертификата | Недоверенный сертификат вызывает отказ |
| Межсервисный доступ | Секрет из окружения, сравнение без утечки времени; отсутствие секрета запрещает запуск внутреннего API | Без заголовка и с неверным значением запрос отклоняется |
| Доступ к данным | Подготовленные SQL-запросы, запрет HTTP-доступа к БД и конфигурации | Проверка инъекций и обращений к закрытым путям |
| Веб-операции | Серверная проверка роли, CSRF-защита изменяющих запросов; Secure, HttpOnly и SameSite для cookie | Прямые запросы от недостаточной роли и без CSRF отклоняются |
| Логи | Только requestId, результат, время и служебные идентификаторы | Нет паролей, токенов, заголовка Authorization и секретов в логах приложения и прокси |
| Целостность выпуска | SHA-256-манифест с доверенной цифровой подписью | Изменённый файл либо недоверенная подпись блокирует установку |
| Антивирусная защита | Проверка готового пакета штатным антивирусом до передачи | Сохранён протокол проверки; отключение антивируса не требуется |
| Копии | Шифрование резервных копий и ограничение прав | Восстановление доступно только ответственному администратору |

Ограничение перебора реализуется на backend независимо по логину и по источнику: 10 неудач на логин за 15 минут и 100 попыток с IP за 15 минут. PHP дополнительно ограничивает 10 неудач по логину за 15 минут. Внутренний API не должен использовать IP backend как IP всех пользователей для общего низкого лимита. Исходный IP определяется backend из соединения; заголовки прокси принимаются только от явно доверенного прокси. Счётчики обновляются атомарно. Записи попыток удаляются спустя 24 часа; аудит административных изменений хранится 90 дней.

Полномочия: пользователь изменяет только свой аккаунт; Admin одобряет и блокирует обычных пользователей; Councilor управляет сотрудниками, но не может лишить систему последнего действующего старшего администратора. Повышение роли запрещено через общедоступные параметры регистрации.

Защита DPAPI не заменяет защиту рабочей станции: процесс, работающий с правами пользователя, может получить доступ к расшифрованной сессии. Поэтому сохраняются ограничение срока и серверный отзыв.

## 10. Инсталляция, настройка и сопровождение — ПК 4.1

### 10.1. Конфигурация

| Параметр | Назначение | Правило |
|---|---|---|
| BackendBaseUrl | Адрес backend для лаунчера | Обязательный HTTPS URL |
| AccountPortalUrl | Страница аккаунта и регистрации | Обязательный HTTPS URL |
| AccountAuthUrl / AccountStatusUrl | Внутренние API сайта | Задаются на backend, не пользователем лаунчера |
| GML_AUTH_SECRET | Общий секрет backend и PHP API | Только серверное окружение, без значения по умолчанию |
| SessionLifetimeHours | Срок сессии | 24 |
| StatusCacheSeconds | Срок кеша допуска | Не более 60 |
| APP_BASE_URL | Публичный адрес сайта | Используется в ссылках подтверждения |
| MAIL_SMTP_* | Почтовый сервер и учётные данные | Секретные значения не входят в репозиторий |

Адреса и секреты являются параметрами развёртывания и не меняют функциональную спецификацию. Приложение проверяет обязательные параметры при запуске и выдаёт диагностическое сообщение без их секретных значений.

### 10.2. Последовательность установки

1. Подготовить закрытый тестовый стенд и зафиксировать версии компонентов в манифесте.
2. Настроить HTTPS, PHP-расширения, права записи БД и запреты доступа к внутренним каталогам.
3. Выполнить резервирование исходных данных и миграцию схемы. Миграции должны иметь номер, выполняться однократно и не изменять существующие UUID.
4. Развернуть API аккаунтов и проверить контракт на синтетических аккаунтах.
5. Развернуть адаптер и управление сессиями backend, задать URL и секрет. Проверить отказ при неверной конфигурации.
6. Собрать Release-пакет лаунчера для Windows x64. Для самостоятельного пакета: `dotnet publish src/Gml.Launcher/Gml.Launcher.csproj -c Release -r win-x64 --self-contained true`.
7. Подписать пакет или манифест, выполнить антивирусную проверку и установить пакет под обычным пользователем на чистую тестовую машину.
8. Выполнить функциональные, защитные, нагрузочные тесты и восстановление резервной копии.
9. Передать готовый пакет, конфигурационный шаблон без секретов и протоколы ответственному за внедрение.

### 10.3. Обновление и откат

Обновление сначала проверяется на стенде. Перед рабочим обновлением сохраняются предыдущие пакеты, конфигурация и согласованная копия БД. Для SQLite используется online backup либо копирование при остановленной записи с учётом WAL; копировать только основной файл активной БД недостаточно.

При нарушении входа или целостности данных внедрение прекращается. Восстанавливается совместимая пара приложения и БД. Изменения пользователей после момента копии учитываются отдельно; потеря таких изменений должна быть явно отражена в протоколе. После восстановления серверные сессии отзываются, пользователи входят повторно.

### 10.4. Сопровождение

Ежедневно проверяются доступность API, ошибки и резервирование. Еженедельно — лимиты попыток, свободное место и аудит доступа. Ежемесячно — восстановление копии и актуальность прав. Перед выпуском — зависимости, лицензии, отсутствие секретов в журналах и совместимость контрактов. Ротация межсервисного секрета выполняется согласованно на двух серверах с проверкой успешного тестового запроса.

## 11. Программа испытаний и критерии приёмки

| ID | Сценарий | Ожидаемый результат | Требования |
|---|---|---|---|
| T-01 | Вход одобренного пользователя с подтверждённой почтой | Сессия создана, UUID соответствует аккаунту | FR-01–06 |
| T-02 | Пустые поля, неверный пароль, неизвестный логин | Локальный либо серверный отказ, без новой сессии | FR-02, FR-04, FR-10 |
| T-03 | Блокировка, неподтверждённая почта, pending и denied по отдельности | Отказ с корректной причиной | FR-04, FR-10 |
| T-04 | Перезапуск с действующим, истёкшим и отозванным токеном | Только действующая сессия восстанавливается | FR-07 |
| T-05 | Выход онлайн и повторное предъявление токена | Локальный токен удалён, сервер отклоняет старую сессию | FR-08 |
| T-06 | Смена пароля, блокировка и отзыв одобрения активного аккаунта | Защищённый API недоступен не позднее 60 с | FR-09, NFR-04 |
| T-07 | Недоступность каждого сервиса и зависшее соединение | Нет защищённого доступа; ошибка до 10 с | FR-13, NFR-03 |
| T-08 | Многократное нажатие входа при задержке | Один запрос, отзывчивое окно | FR-11, NFR-07 |
| T-09 | Прямой административный запрос обычного пользователя | Отказ; успешные административные изменения отражаются в аудите | FR-12, FR-14 |
| T-10 | Перебор по одному логину и по разным логинам с одного IP | Срабатывают независимые лимиты и Retry-After | Раздел 9 |
| T-11 | Неверный секрет, сертификат, формат и метод запроса | Контрактный отказ без выдачи токена | Разделы 7, 9 |
| T-12 | Анализ локальных файлов и журналов, копирование токена другому пользователю ОС | Отсутствуют открытые секреты; копия не расшифровывается | Раздел 9 |
| T-13 | Нагрузка и измерение времени входа | Выполнены заданные p95 и доля ошибок | NFR-01–02 |

Протокол каждого теста содержит дату, исполнителя, версии, исходные условия, действия, фактический результат и обезличенное подтверждение. Приёмка требует прохождения всех обязательных сценариев, выполнения численных критериев и отсутствия дефектов, позволяющих обойти допуск или раскрыть секреты. Испытания в рамках этого предпроектного документа не выполнялись.

## 12. Инженерные компромиссы

| Решение | Обоснование | Недостаток и способ его учёта |
|---|---|---|
| Backend как посредник | Сохраняется единая точка доступа для лаунчера и централизованная выдача сессий | Дополнительная зависимость; тестируется вся цепочка, задаются тайм-ауты |
| SQLite | Упрощает установку и резервирование небольшого проекта | Конкуренция записей; пригодность подтверждается нагрузкой, при превышении — отдельная миграция |
| Проверка статуса с кешем до 60 с | Снижает нагрузку без длительного сохранения отозванного допуска | Блокировка не мгновенная; предельная задержка закреплена в требованиях |
| Запрет доступа при недоступности проверки | Не позволяет использовать непроверенную сессию | Снижается доступность при сетевом сбое; остаётся локальный интерфейс |
| DPAPI и Windows x64 в первой версии | Позволяет реализовать защиту без собственного хранения ключей | Для других ОС требуется отдельный адаптер |
| Сессия 24 часа без продления | Ограничивает срок использования похищенного токена и упрощает протокол | Пользователю нужно периодически входить заново |
| Подтверждение почты и ручное одобрение | Соответствует управляемому допуску в проект | Дополнительные действия и ожидание; статус отображается в аккаунте |
| Самостоятельный пакет .NET | Упрощает установку пользователю | Больший размер и обновление runtime вместе с приложением |

## 13. План реализации и комплект передачи

1. Подготовить схему данных, миграции и правила допуска.
2. Реализовать API проверки пароля и статуса, ограничения попыток и аудит.
3. Реализовать адаптер backend, серверные сессии и отзыв.
4. Реализовать форму входа, API-клиент и защищённое хранение.
5. Настроить развёртывание и резервирование.
6. Выполнить испытания и устранить выявленные дефекты.
7. Передать результат для внедрения.

Результат этапа проектирования — настоящая спецификация. Результат последующей разработки — исходники, миграции, пакет лаунчера, серверные модули, шаблоны конфигурации, реестр зависимостей и лицензий, инструкция установки и отката, подписанный манифест и заполненные протоколы испытаний.

Выбранные правила допуска, сроки сессий, API и критерии приёмки являются исходными условиями учебного проекта. Их изменение оформляется новой версией спецификации. Значения адресов, секретов и точных сборок заполняются в конфигурации стенда; они не требуют изменения бизнес-логики.
